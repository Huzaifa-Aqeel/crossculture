# CrossCulture build plan — Brand × Brand commerce

## Adaptive learning — decided design (25 October, supersedes the earlier feedback-first plan)

**Outcome:** the app gets measurably better at finding good Brand × Brand opportunities with every run. Learning changes only *what is researched first, what is skipped and how the research budget is spent*. Evidence gates, assessment status and the `brand-commerce-v1.1` displayed ranking are unchanged; every opportunity is still verified live. The hosted database started empty on 25 October, so the first learning source must not depend on users.

**User decisions (25 October):** (1) research memory before feedback controls; the cross-user learned policy is parked until there is real traffic. (2) Research memory is shared across users, keyed by partner store and public Shopify taxonomy category only. (3) The user adjudicates the review queue for loop 2.

### Loop 1 — research memory (no users needed)

- Each run records the app's own decisions per researched partner in server-only tables: partner Qloo ID and verified shop ID, objective, market, the starting product's Shopify taxonomy category, outcome (`identity_unverified` with a lasting reason, `no_product_value`, `researched`, `incomplete`), the catalog screen decision, assessed/recommendable/Supported counts, Catalog calls, and one row per assessed pair (hashed opportunity key, partner product taxonomy category, status, mechanism gate, reason codes, model).
- **Never stored:** user ID, starting brand, product titles/descriptions/collections, prices, availability, images or any Catalog payload. Taxonomy category IDs come from Shopify's public Standard Product Taxonomy (`categories[].value` on storefront products). Field audit under Architecture §10: these are non-prohibited decision metadata, not a product index.
- **Uses (1a, built first):** (i) partner order — partners with Supported pairs for a similar starting category (shared taxonomy prefix) go first; partners researched twice for a similar category with nothing recommendable go last; Qloo order and the description triage still order the rest; at most two proven partners run before an unexplored one. (ii) Lasting identity failures (site name absent, no Shopify store, no official site found) are skipped for 7 days unless a verified website exists; network, timeout and HTTP 403/5xx failures are never remembered. (iii) Catalog screen decisions are reused for 6 hours from Postgres, replacing the in-process map that Lambda loses. (iv) An exact pair the same judge (model plus judgment prompts and rules, versioned automatically) rejected within 7 days is not judged again; supported mechanisms are always re-assessed. Memory is reused only for partners already present in the current user's own Qloo results and never adds a partner. Rows older than 180 days are purged.
- **1b (next):** learned search directions — partner product categories and mechanism roles that produced Supported pairs for a similar starting category become early search plans; consistently empty directions move last. Still verified live.
- **Measure:** Supported pairs per 100 Catalog calls, calls to first Supported pair, partners researched with no result, repeat-verdict agreement. Computed from run records; compare runs before and after memory on the same US seeds.

### Loop 2 — judgment calibration from real cases

- Detect verdict flips for the same opportunity key across runs, plus a sample of Supported results, into a developer-only review queue. The user adjudicates good/bad with a short note.
- Adjudicated cases join `eval:mechanism` (dev and holdout) and become retrieved examples in the pair judgment by nearest category pair. A new example set or prompt ships only when the evaluation does not regress. Only human-adjudicated labels are used; the model's own verdicts never become labels.

### Loop 3 — user signals (personal)

- Interested and Pass with an optional reason on each opportunity card; proposal written/edited/downloaded is the strongest positive signal. Pass "Products don't fit" → personal negative for that category pair and a loop 2 review candidate; "Already working with them" or "Not relevant" → project-scoped partner exclusion; "Cultural connection unclear" → review candidate.
- The worker must actually read the run's preference snapshot: today `feedback_snapshot_json` and `excludedPartnerEntityIds` are stored at run creation but never used by research. Replace the fire-and-forget save after proposal creation with an awaited action.

### Loop 4 — cross-user learned policy (parked)

Consent, exposure logging, a scheduled aggregate learner and a randomized exploration slot wait until there are enough independent users. A fine-tuned model, collaborative filtering and click-based ranking remain out of scope; a change to displayed ranking requires a new scorer-policy decision.

## Research breadth (25 October)

Each partner stops after 3 Supported pairs, or after 8 assessed pairs with nothing worth showing, so the run budget reaches more partners. A partner's own allowance, store failure or early stop never ends the run.

## Apparel wearer rule (25 October, user decision)

Doubtful apparel pairs are dropped, not shown, and a Bundle never contains a fit-sized item (sized products are not offered for Bundle): see Scoring Engine "Wearer" and "Fit sizes in a Bundle" (amended 25 Oct).

## Lambda research dispatch (25 October)

- **Confirmed deployment decision:** Vercel hosts the Next.js frontend. AWS hosts separate API and research Lambda functions. Supabase `analysis_runs` remains the only application job queue; there is no SQS queue or Supabase webhook in the final path.
- The API inserts a queued run and commits it, then calls the worker Lambda with `InvocationType=Event` using the AWS SDK. The API's execution role needs `lambda:InvokeFunction` for only that worker function. The worker's `src/research-lambda.mjs` handler claims one ready row through the existing `FOR UPDATE SKIP LOCKED` lease logic and writes the result. An EventBridge Scheduler `rate(1 minute)` invocation of the same handler recovers missed invokes, due retries and expired leases. Duplicate invokes are harmless because the event is a wake hint and Postgres decides which row is claimed.
- `RESEARCH_WORKER_FUNCTION_NAME` configures dispatch on the API Lambda. The API returns the queued run even if the async invoke fails after commit; the scheduled recovery handles it. Local development without that variable still runs the in-process worker and a 60-second recovery scan. The API Lambda must not run the local timer. Before deployment, package the HTTP API with the Lambda Web Adapter (or another HTTP adapter), set worker timeout and memory from measured live runs, configure the scheduled trigger and verify the API-to-worker IAM permission, then run an end-to-end signed-in research check.
- **Worker concurrency:** the deployment tries to reserve two concurrent executions for the research Lambda, allowing two jobs to run in parallel while capping provider and database load. AWS requires at least 10 unreserved account executions; this account currently has a total quota of 10, so reservation cannot be applied. The worker uses shared concurrency and Postgres `FOR UPDATE SKIP LOCKED` still lets distinct runs proceed concurrently when capacity is available. Request an account concurrency quota of at least 12 before applying the two-execution reservation. The worker setup command checks the quota and reports when it must use shared concurrency.
- **AWS deployment checkpoint:** the API exposes a `serverless-http` Lambda handler and the published Qloo MCP harness is a package dependency, so both Lambdas use one 39.5 MiB ZIP built with `npm run aws:package`. The three IAM roles, worker and API Lambdas, public API Function URL, and one-minute Scheduler target are deployed in `us-east-1`. The API URL health check returned 200. The Vercel proxy still returns 503 because `CROSSCULTURE_API_URL` has not been configured there; set it to the deployed Function URL without a trailing slash, redeploy, then run a signed-in hosted research check. The hosted web profile at `https://culture-circle.vercel.app/ucp-agent-profile.json` is verified and configured for Lambda.
- Migration `202610250001_research_wake_webhook.sql` was briefly applied to hosted Supabase while an always-on Node worker was planned. Forward migration `202610250002_remove_research_wake_webhook.sql` drops its trigger and function without changing run rows. No webhook URL or secret is needed in Vault.

## Brand country, where to launch and guided flow (24 October)

- **Brand country.** The user enters the brand and its country first. The country sets the project market (stored on `projects.market`), currency and Catalog market, and adds one country-domain guess after `brandname.com`. If the brand cannot be confirmed in that country, the user sees an honest limitation and can enter the official website.
- **Where audiences overlap** (formerly "Where to launch"). For a saved or shown opportunity, both brands' Qloo where_popular results within the project country are mapped to named metro areas; shared areas (up to four) are shown on the card and in the proposal and given to concept development. Explanation only — no effect on status or ranking.
- **Guided flow and results UI.** Brand + country → goal (and optional chosen partner) → chosen product → optional refinements. Results show only the essentials per opportunity; evidence, sources and reviewed products stay behind a details disclosure.
- **Still open:** market-tuned partner discovery (`signal_location`) — a UK probe reshuffled partners but they were still US brands, so it is on hold pending a non-US brand test.

## Must-fix pass after the launch review (24 October)

- **Compare Two Brands:** a chosen partner found in Brand A's unconstrained Qloo recommendation read to 20 results (the provider maximum; 25+ is rejected) is a native recommendation. If not, Brand A in the partner's own top-20 recommendation (anchored on the partner per Qloo's explainability) supports the pair as `direct_pair_supported`. Otherwise the strict shared-tag rule applies, which most brands cannot meet because their Qloo tags are audience tastes rather than brand attributes.
- **Consistency:** a partner rejected by the catalog screen is re-screened with one more catalog page before being dropped; screen decisions are reused for six hours per chosen product, objective and partner shop (a boolean keyed by IDs, no Catalog content); a judgment whose verdict and own fields disagree is asked once more and only a consistent second answer is kept.
- **Model resilience:** Bedrock uses adaptive retries (4 attempts). The OpenAI-compatible fallback now reads `GROQ_MODEL` and no longer sends `enable_thinking`, which Groq rejects; a live fallback call answered.
- **Scoring Engine aligned:** §0 (chosen product required), §2 (decision-level evidence for the MVP), §3.2 (top-20 native check) and §4 (implemented Bundle link, apparel, care and fit rules).

## Simplification decisions (24 October, latest)

User decisions, now implemented:
- **Chosen product required.** Every Find Partners and Compare Two Brands run starts from one chosen starting product. The API rejects runs without one, the worker treats them as permanent errors, the UI keeps the start button disabled until a product is chosen, and the no-product research branches and their query helper are deleted.
- **Brand identity.** Every brand tries a saved verified website, the Qloo website (or the one the user entered), then `brandname.com` (also with "&" as "and"); a site passes when its own name (HTML entities decoded) contains the brand name as whole words and it links its own Shopify store. A starting brand or a user-chosen Compare Two Brands partner never searches: when those sites fail, the user enters the official website. A Qloo-suggested partner falls back to one web search for "brand + up to two Qloo-description words + official website", preferring a result whose address contains the brand name, otherwise the first result that is not a social, marketplace, reference, review, press or blog site; the same two checks apply and the verified website is saved.
- **Item-type compatibility proof.** A fit or compatibility claim is confirmed when a trusted product page names the other item's type or material ("fits over helmets", "for leather boots") or its exact title; direct functional pairs no longer need a named occasion.
- **Bundle links.** Without a direct function, two items must handle the same thing (pan and pasta bowl), or both pages must name the same activity, verified against the page text. A shared meal, party or room is not enough. Two apparel/personal-accessory items need a direct function.
- **Partner value screen.** Qloo brand descriptions only order discovered partners (likely → possible → unlikely); a live run showed they are too thin to drop a partner (Arhaus is described as furniture but sells dinnerware). Every discovered partner is instead screened against its real catalog sample and the exact chosen product right after the first catalog pages; a partner with nothing of value stops there (about 5–7 Catalog calls instead of up to 56). Exclusions: unrelated product worlds, substitutes, decor/ambience only, clothing styling for a Bundle, generic gifting/lifestyle. If every verified partner is screened out, the run completes with `no_partner_product_fit`. A failed screen never drops a partner; Compare Two Brands is not screened.
- **Learned brand websites.** An official website verified for a Qloo brand (by a user's confirmation or an earlier run) is tried first for that brand as a partner, and at confirmation when Qloo lists no website; it is still re-verified.
- **Partner concurrency.** Two discovered partners are researched at a time (`COMMERCE_PARTNER_CONCURRENCY`), each up to the per-partner time limit and the run's remaining time, with an even split of the remaining Catalog budget; a rate limit, time limit or exhausted budget stops new partners from starting. Time is not pre-split by partner count: a live run showed that starved the one partner that passed the screen.
- **Occasion and preferences.** Search planners, the partner filter and the judgment receive the stated occasion and preferences. The judgment reports whether a pair serves the occasion and quotes supporting product text for each preference (quotes verified in code); ranking uses these answers. They never change a verdict.
- **Qloo in explanation and concepts.** Discovery takes Qloo's top 12 brand recommendations (one request, `limit: 12`). Qloo's explainability for a single brand signal only attributes every recommendation to that signal, so it cannot name a theme. Both brands' Qloo entity tags are fetched instead (replacing an unused per-partner rank call): a shared brand-attribute tag (aesthetic/keyword namespace) names a broad theme, or a specific one when the selected products' text corroborates it, which feeds ranking criterion 3. Shared cross-domain audience tastes (media and music genres, food, media keywords; payment, price, rating and generic words removed) are shown under Cultural connections, used by the audience panel and passed to concepts, but never change status or ranking (Scoring Engine 3.3). Raw Qloo affinity is not used in ranking (Scoring Engine 7).
- **Tavily scope.** Public-source partner review runs once when the user saves an opportunity (three parallel searches, at most 8 seconds, never changes status or rank) instead of automatically during research. The dated seasonal concept search is removed. Tavily remains in the Compare Two Brands cultural check (shared Qloo tag corroborated on both official sites) and in the disabled non-native product-context path.

Evaluation after these rules (72 synthetic pairs, 3 runs each): Bundle good 85% / bad 0%, Cross-Sell good 98% / bad 0%. Known Bundle misses: rain jacket + daypack (co-wear), picnic blanket + cooler (no shared object or activity text), journal + wind-down candle (the judge returns parallel benefits although both pages name the ritual). The final rule set has not yet had a live run.

## Product-mechanism quality: labelled evaluation and judgment fix (24 October)

A labelled evaluation now measures the app's own pair review: 64 hand-written synthetic pairs (`api/fixtures/commerce-mechanism-eval-v1.json`), three runs each, with a 24-pair holdout frozen before any run. Labels were written by Claude against Scoring Engine §4/§5 with a reason per pair; they are a regression and consistency measure, not the human-adjudicated precision §11 still requires. Results and method: `api/reports/commerce-mechanism-eval-v1.md`.

Finding: several prompts embedded `Return exactly {"field":true,...}` templates and the model copied the values. The Bundle counterfactual therefore rejected every Bundle since 21 October (dev good-Bundle pass rate 3%), while the Bundle/Cross-Sell challenges and the concept review approved everything. A keyword rule also blocked real bundles whose text mentioned coat, clean, wash or similar words.

Implemented: one objective judgment per pair replaces the stacked challenges; the server combines its fields (same product type → substitute; mood/ritual outcomes need both items' own text to name the activity, otherwise the result must be practical). No prompt carries an example answer, and a check enforces this. The compatibility rule now applies only to treatment/care-product roles; explicit fit/compatibility claims still need merchant-authored proof. The concept review must quote the unsupported phrase or say "none". `evaluateCommerceMechanism` is the shared pair review used by live research and the evaluation. Discovered partners are ordered by a product-fit hint from Qloo descriptions (likely → possible → unlikely) before deep research; none are excluded and a failed hint keeps Qloo order.

Live runs then exposed two false-positive patterns, fixed with rules from Scoring Engine §4: two apparel or personal-accessory items form a Bundle only when one acts directly on the other (outfits remain Cross-Sell candidates), and a care product for the other item needs its own trusted text to name that item's type, or an exact merchant compatibility statement when either page has a restrictive care instruction. Final measurement: dev Bundle good 67% / bad 0%, Cross-Sell good 100% / bad 0%; holdout Bundle good 100% / bad 0%, Cross-Sell good 89% / bad 0%. Live: Everlane shirt Bundle 7 co-wear Supported → 0; Caraway pan Bundle laundry-bleach Supported → pan + dinnerware set and pan + cutting board; Everlane shirt Cross-Sell 8 Supported; Our Place found no kitchen-related Qloo partner. Next: human labels on a sample; require or default a chosen starting product (the no-product path reviews only 4 arbitrary pairs per partner); decide whether to relax the exact-title fit rule for equipment pairs; decide whether brand search should skip social profiles (Our Place's top result was Instagram).

## Entry, run-time and API reliability pass (24 October)

Implemented after an engineering review of the Brand × Brand path. Brand-site identity checks now follow up to three redirects. Product research itself stays one partner at a time so the shared Catalog budget and rate-limit stop remain exact.
